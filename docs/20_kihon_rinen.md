# 基本理念: 大きな仕様を一気に作らせない、小さく作って自分で使う

## 原文の要点

### 1. 大きな仕様書を書いて一気に作らせない

- まだ無いものの仕様書は書けない。仕様書は知っていることをまとめたもので、新しいことを見つける道具ではない
- 宝くじのたとえ: 1項目が9割うまくいくとしても、全部うまくいく確率は 3項目で約7割、10項目で約3.5割、20項目で約1割（単純な計算で、桁の感覚をつかむための数字）。しかも外れは、作り終えて触るまで分からない
- 仕様を細かく書くほど、実装を先に書いているのと同じになる。仕様書は動かないので、正しいかどうかを教えてくれない
- AI で書き直しが安くなったので、紙の上で詰めるより、作ってから間違えるほうが安い。ただし、データの移しかえ、外に公開する決まりごと、外部とのつながりなど、作り直しが高いものは先に詰める

### 2. 仕様ではなく、実装を小さく詰める

- 判断が必要な一番小さい単位に切り、1つずつ作って、そのたびに判断する
- よいこと: 1つずつ見るほうが判断が正確 / 途中で方向を変えられる / 早く人に触ってもらえる
- ただし、切り方をまちがえると、つなぎ目に新しいまちがいが入る

### 3. 作ってみないと出てこない決定がある

- 筆者のツールは、作る前に思っていた目的と、使った人が感じた価値がちがった。通知が多すぎて止めた人がいた、など、作る前には分からなかった
- AI がもっともらしい理由で出した判断も、自分で実物を確かめたら逆だった例がある。実物を見るまで正しいかは分からない

### 4. AI は「決める人とコードの距離」を縮めない

- AI が速くするのは実装。仕様のまちがいは減らない。まちがった仕様が、より速く形になるだけ
- 大事なのは、決める人がコードの近くにいること。「AI にレビューさせればいい」は解決にならない
- AI は倍率をかける道具で、元の力（何が欲しいかを持つ、出てきたものを選ぶ）は自分しだい

### 5. 作る単位は小さく、でも意見と利用者は多く

- 1つのプロダクトを作る人は 1〜3人が目安（形が決まっていない、持ち主が自分で触れる、などの条件つき）
- 小さくするのは「作る単位」だけ。アイデア、意見をくれる人、使う人の数は多いほうがよい

### 6. まとめ

- 持ち主が少人数で、自分で細かく使いながら作るのが、AI の時代に向いたやり方
- 持ち主が一番のヘビーユーザーであること。使っていないと、利用者の声の重みも分からない
- 必要なのは、コードを速く書く力ではなく、**「何が欲しいか」を持つことと、出てきたものに「違う」と言えること**。プログラミングが得意でなくても、この2つがあればできる
- ただし AI に丸投げしない。細かいところまで自分で見て決める

## このプロジェクトへの当てはめ

| 原文の考え | このプロジェクトでやること |
|---|---|
| 大きな仕様を一気に作らせない | docs/19 の候補などは、1つずつ小さく作る。1回の作業で1つの変更にする |
| 判断が必要な単位で切り、そのたびに判断する | 1つ作ったら、ユーザーがスマホで触って「これでいい / 違う」を決めてから次へ |
| 作ってみないと分からない | 仕様を詰めすぎない。まず動くものを出して、親に使ってもらって直す（方針 3、docs/17 の 2-(1)） |
| 作り直しが高いものは先に詰める | 記録の保存のしかた（端末の中のデータの形）、飲み合わせの表の出どころと許可（docs/19_kyoka_irai）、個人情報の扱いは、先に考えて決める |
| AI の判断をうのみにしない | 薬の情報は出どころを確かめ、薬剤師（ユーザー）が中身を確認する（CLAUDE.md「守ること」） |
| 持ち主が一番のヘビーユーザー | ユーザー自身が親として毎日使う。「うちではこう使っています」と言える状態にする（方針 2） |
| 意見と利用者は多く | メンター・参加者の意見を docs/18 に集める。知り合いの親に毎週使ってもらう |
| 「何が欲しいか」と「違う」と言う力 | 迷ったら「それで子どもが飲むようになるか」で決める。違うと思ったら、作ったものを捨ててよい |

関連: CLAUDE.md の方針 6（メンターの助言「まず小さく作って、Vibe Coding とハーネスを学ぶ」。docs/18 の 3）は、この記事と同じ考え。
